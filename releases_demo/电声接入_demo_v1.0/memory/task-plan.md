# 任务计划

> 由总控工作流或项目拆分智能体维护。用于描述面向人的实施计划，不替代 `memory/execution-steps.md`。

## 项目目标

- 构建并交付 **电声接入_demo_v1.0** 静态演示原型，展示外呼中台与电声AI平台的对接闭环。
- 完成前台各核心模块的电声适配（新建场景呼叫任务配置配置与提交生成外呼任务、列表三页签详情、已过滤原因分类、通话/线索记录字段强化等）。
- 实现以电声 API 字段为支撑的 Mock 数据流转，提供流畅的演示体验。

## 阶段计划

1. **第一阶段：准备与基础架构（Step 01）**
   - 确认项目根目录静态结构，修改导航配置文件以展现电声模块。
2. **第二阶段：内存数据与 Mock 驱动（Step 02）**
   - 全面重构 `mock/data.js`，设计符合电声线索/话单 API 结构的模拟内存数据库与状态发生器。
3. **第三阶段：业务场景配置管理（Step 03）**
   - 修改业务场景页，支持“电声”平台的建立，简化通道与加微选项，配置呼叫任务配置并在提交时生成外呼任务 `strategyCode`。
4. **第四阶段：外呼任务详情与名单（Step 04）**
   - 改造外呼列表及查看详情，实现“数据概览”、“任务详情”及“呼叫名单”五个子 Tab 的分类展示与终止外呼动作。
5. **第五阶段：外呼结果与线索明细（Step 05 - Step 06）**
   - 增强通话记录与线索记录，展示通话状态、挂机小结与回访明细；“是否重拨”按执行明细已拨打次数派生，通话记录列表不展示线路类型和加微状态。
6. **第六阶段：统计报表与全局对账验证（Step 07）**
   - 适配通话统计页面，整合展示电声场景/执行批次维度的外呼与客户指标。

## 当前优先级

- **当前任务**：S6 拆分任务通过后，进入 S7 逐步执行各开发步骤并进行单步验证。

## 风险与依赖

- **Mock 闭环依赖**：所有前台页面均通过 Fetch 和本地 JS 对象加载 Mock 数据。必须保证 `mock/data.js` 改动先行，否则后续各页面渲染都会因为缺少对应字段（如 `answerStatus` 等）而失效或报错。
- **静态资源依赖**：必须在本地使用 Python 的 HTTP Server 启动服务，否则导航菜单等动态 JSON 加载将受限于浏览器跨域安全策略。
